# Product Auth — Telegram, v0.1.0

Независимый модуль входа для проектов на Python/FastAPI. Общий код, но отдельные пользователи, сессии, база, Telegram-приложение и настройки в каждом продукте.

**Статус:** рабочая первая версия, проверяемая локальными автоматическими тестами. Вход через ваш реальный Telegram-бот ещё не проверен. Это не аудит безопасности и не готовый публичный сервис: до публикации обязательны HTTPS, ограничения частоты запросов и проверка реальной интеграции.

**Не переносите эти файлы внутрь `resolute_app__raw_app`.** Это отдельный серверный пакет, не замена React-приложения Windmill. Существующий Windmill и его настройки не меняются.

## С чего начать

1. Распакуйте архив. Папку `product-auth` можно положить в `/Users/andrew/Dev/telegram-parser/` как отдельный модуль.
2. Откройте папку в VS Code. Python должен быть версии 3.11 или новее.
3. Установите пакет в отдельное виртуальное окружение:

```bash
cd /Users/andrew/Dev/telegram-parser/product-auth
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -c constraints-tested.txt -e '.[sqlite,demo,test]'
cp .env.example .env
```

Если пакет кладёте в другой каталог, используйте его путь в `cd`.

4. В `.env` заполните настройки своего продукта. Не отправляйте этот файл и секреты в чат, Git или React-код.
5. Создайте таблицы миграцией:

```bash
product-auth migrate
```

6. Запустите пример:

```bash
uvicorn examples.app:app --host 127.0.0.1 --port 8000 --no-access-log
```

Для локального HTTP в `.env` нужны `AUTH_ORIGIN=http://localhost:8000`, `AUTH_DEVELOPMENT=true` и `AUTH_COOKIE_NAME=your_product_session`. Пример откроется по `http://localhost:8000`, однако настоящий вход с таким адресом зависит от разрешённых URL в Telegram. Надёжный вариант интеграционного теста — отдельный зарегистрированный HTTPS-адрес, направленный на этот сервер через защищённый reverse proxy или туннель. Не публикуйте весь Windmill через этот туннель.

**Не подставляйте фиктивный HTTPS-домен ради прохождения проверки настроек:** браузер должен действительно открывать этот адрес, иначе cookie и callback не заработают. Серверу нужен доступ к `oauth.telegram.org`; при ограничениях сети понадобится работающий VPN/прокси. HTTPX поддерживает переменные `HTTPS_PROXY`/`ALL_PROXY`, включая SOCKS через установленную зависимость. У браузера и Python-сервера доступ проверяется отдельно.

В примере отключён access log, чтобы одноразовый код из callback не попадал в журналы. На внешнем reverse proxy тоже отключите или редактируйте query string для `/auth/telegram/callback`.

## Настройка Telegram

Официальная документация: https://core.telegram.org/bots/telegram-login

1. Создайте или выберите бота своего продукта в BotFather.
2. Откройте Login Widget / Web Login.
3. Зарегистрируйте origin сайта и точный callback: `https://ВАШ-ДОМЕН/auth/telegram/callback`.
4. Внесите Client ID и Client Secret в `.env`. **OIDC Client Secret не является Bot API Token.**
5. Оставьте алгоритм подписи ID token **RS256** — пакет намеренно принимает только его.
6. Проверьте вход в новом окне браузера, повторный вход, выход и закрытый API.

Scopes — только `openid profile`. Телефон не запрашивается. Разрешение боту отправлять сообщения пока не запрашивается: уведомления подключаются отдельным шагом. OIDC `sub` не приравнивается к числовому Telegram `id`: оба сохраняются отдельно.

## Как работает модуль

1. `GET /auth/telegram/start` создаёт одноразовый вход: случайные state, nonce и PKCE verifier. На сервере сохраняется запись на 10 минут, в браузере — отдельная HttpOnly cookie, связывающая вход с этим браузером. Открытие второго входа в том же браузере заменяет первый незавершённый вход.
2. Authlib формирует переход на Telegram с PKCE S256.
3. Callback атомарно потребляет одноразовую запись. Чужой браузер без соответствующей cookie или повторный запрос не может завершить вход.
4. Сервер обменивает code на token с Client Secret. joserfc проверяет RS256-подпись по фиксированному Telegram JWKS; Authlib проверяет OIDC claims, включая issuer, audience, время и nonce. UserInfo endpoint не вызывается.
5. Аккаунт находится по Telegram OIDC subject или создаётся. Username не является ключом аккаунта.
6. Создаётся случайный session token, его SHA-256 хранится в базе. Сырой token находится только в защищённой cookie. Telegram access/ID tokens не сохраняются.
7. `GET /auth/me` проверяет срок сессии и активность пользователя и возвращает публичные данные и CSRF token.
8. `POST /auth/logout` проверяет Origin и CSRF, удаляет сессию и cookie.

Cookie: HttpOnly, SameSite=Lax, Secure на HTTPS, host-only, без Domain. В production рекомендуется имя с `__Host-`. Срок сессии абсолютный (по умолчанию 7 дней), не продлевается каждым запросом. Выйти — завершить текущую сессию; остальные устройства автоматически не отключаются. Если администратор устанавливает `auth_users.active=false`, все сессии этого пользователя перестают давать доступ.

## Подключение к другому FastAPI-приложению

```python
from fastapi import FastAPI, Depends
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker
from product_auth import AuthModule, AuthSettings, User

settings = AuthSettings()
engine = create_async_engine(settings.database_url.get_secret_value())
sessions = async_sessionmaker(engine, expire_on_commit=False)
auth = AuthModule(settings, sessions)
app = FastAPI()
app.include_router(auth.router)

@app.get('/api/profile')
async def profile(user: User = Depends(auth.require_user)):
    return {'id': user.id, 'name': user.name}
```

В реальном приложении добавьте lifespan для закрытия engine, TrustedHostMiddleware и no-store для персональных ответов — полный пример в `examples/app.py`. Миграции запускайте отдельной командой при развёртывании, а не в каждом worker. Для PostgreSQL установите extra `postgres`; PostgreSQL URL должен использовать `postgresql+asyncpg`.

Вместе с пакетом поставляется первая миграция. Новые версии модуля должны добавлять новые миграции, а не переписывать старую. Используется отдельная таблица `auth_alembic_version`, чтобы не конфликтовать с миграциями продукта.

**Каждый защищённый endpoint должен подключать `Depends(auth.require_user)`.** Для POST/PUT/PATCH/DELETE dependency также требует точный Origin и `X-CSRF-Token`. Нельзя получать ID владельца из тела запроса и доверять ему. Используйте `user.id`, а затем проверяйте права на конкретный объект. Модуль подтверждает личность, но не реализует тарифы и бизнес-права.

Cookie сама по себе не заменяет серверную проверку. Не используйте изменение `isLoggedIn` в React как контроль доступа.

## Подключение React

Файлы `frontend` — отдельные заготовки для **самостоятельного React-приложения на одном origin с FastAPI**, не для прямой вставки в public app Windmill.

Вызовите `useAuth()` один раз выше страниц. Передавайте результат через props или контекст. Различайте `loading`, `anonymous`, `authenticated`, `error`: ошибка сети не должна маскироваться под отсутствие аккаунта.

- На `anonymous` покажите `LoginPage` с `onLogin={auth.login}`.
- На `authenticated` показывайте приложение.
- На `error` предложите повторить `auth.refresh()`.
- Для выходa вызывайте `await auth.logout()`, обработав возможную ошибку; очистите также пользовательские данные продукта в React.

Защищённый запрос:

```typescript
const response = await fetch('/api/favorites', {
  method: 'POST',
  credentials: 'same-origin',
  headers: {
    'Content-Type': 'application/json',
    'X-CSRF-Token': auth.csrfToken!,
  },
  body: JSON.stringify({ post_id: 123 }),
});
```

Вызывайте его только при `auth.status === 'authenticated'`. При 401 обновляйте состояние авторизации и очищайте данные прежнего пользователя. Не храните session token в localStorage. Уведомления об изменении сессии между вкладками пока не реализованы: сервер проверяет сессию на каждом запросе, но UI другой вкладки может обновиться позже.

## Граница с текущим проектом Windmill

Пока модуль **не подключён** к вашим контролям, избранному и скриптам. Он добавляет независимый пример входа. Следующая интеграционная задача — вынести пользовательский React-сайт из Windmill, направить запросы через FastAPI и поставить проверки пользователя на каждом endpoint. Прямые публичные вызовы привилегированных скриптов нужно закрыть. До этого не включайте `No login required` в существующем приложении.

Существующие React-компоненты и скрипты можно сохранить. Конкретное подключение потребует актуальных `package.json`, `index.tsx`, конфигурации приложения и серверной структуры; не присылайте `.env`, browser profile, session cookies или секреты.

Сессия входа разделяется вкладками одного браузера через cookie. Состояние React при этом у каждой вкладки отдельное.

## Тесты и проверка пакета

```bash
python -m pytest -q
```

Тесты не отправляют данные Telegram и не требуют бота. Они подставляют HTTP-ответы Telegram, но создают и проверяют настоящие RSA-подписи. Проверяются state/browser binding, PKCE, nonce, issuer, audience, срок токена, подпись, повторный callback, CSRF, отзыв/истечение сессии, заблокированный пользователь, повторная регистрация и независимость продуктов.

Прогнаны 25 серверных тестов, Ruff, компиляция Python и TypeScript-проверка React-файлов. Собран wheel и проверена миграция из установленного wheel.

В этой среде проверены SQLite и Python 3.12. Для локальной базы нужен SQLite 3.35+ (используется DELETE RETURNING). Перед production на PostgreSQL отдельно прогоните миграции и нагрузочные/интеграционные проверки на выбранной версии PostgreSQL. Реальные входы Telegram и reverse proxy не проверены.

Authlib 1.8 может выводить предупреждение о переходе своего HTTP-клиента с httpx на httpx2. Текущая версия использует поддерживаемую совместимость с httpx, закреплённую диапазоном Authlib <2; обновление транспортной зависимости должно пройти те же тесты. Проверка JWT использует актуальную joserfc, а не устаревающий authlib.jose.

## Перед открытием пользователям — обязательно

- Настоящий зарегистрированный HTTPS origin, правильная цепочка TLS и доверенных прокси.
- Ограничение частоты и размера запросов на reverse proxy, особенно `/auth/telegram/start` и callback. Встроенного распределённого rate limiter в v0.1 нет; без него не публиковать.
- Отдельные секреты, база/роль и cookie для каждого продукта. Не используйте общую auth-базу, если нужны независимые аккаунты. Для продуктов на одном host выбирайте разные cookie names; предпочтительны разные host.
- Не задавайте wildcard CORS с credentials. По умолчанию CORS не включён; предполагается same-origin.
- Не записывайте query code, cookie, Client Secret, token или полные OIDC payload в логи и error trackers.
- Ограничьте доступ роли БД к таблицам своего продукта; настройте резервные копии и восстановление.
- Настройте периодическую `product-auth cleanup` (например, ежедневно) и мониторинг ошибок без чувствительных данных.
- Проверьте каждый продуктовый endpoint на авторизацию и проверку владельца, включая чтение, экспорт и фоновые задания.
- Проверьте блокировку пользователя, удаление аккаунта согласно правилам продукта, сценарии нескольких устройств и восстановление доступа при потере Telegram. Почта и восстановление аккаунта здесь ещё не реализованы.
- Проведите независимое ревью безопасности перед коммерческим использованием. Наличие тестов не равнозначно аудиту.

## Как переиспользовать

На первом шаге пакет устанавливается локально через `pip install -e ...`. Затем вынесите его в отдельный приватный Git-репозиторий, выпускайте версии и подключайте фиксированные теги/commit или wheel в каждом продукте. В архиве есть wheel v0.1.0. Архив не создаёт Git-репозиторий и ничего не публикует автоматически.

Не копируйте секреты и базу из продукта в продукт. Общим является код и тесты, а не учётные записи.
